# Vision

static-assets is the shared origin for the images, fonts and stylesheets the
jointhefreeworld projects reference: one host, one deploy, no page asking a third
party for a file. It is the least glamorous repository in the collection and the
one every other site depends on when it renders. This document says what that
host should become — addressable, derived, verifiable — and which parts of it are
currently a plain copy of a directory.

## Where static-assets is today

A served tree. `static-assets/` holds thirty-seven directories — thirty-four
project folders, plus `fonts/`, `api-docs/css/` and an `other/img/` bucket — with
202 files, about 217 MB, of which 153 are PNG. Some directories are a project's
logo and its `-small` companion; others are screenshot galleries (`sss/`,
`lambdock/`, `heks/`); others a single image referenced from a README.

The fonts are the part done properly. `static-assets/fonts/` carries Work Sans,
Source Serif 4 and JuliaMono as `woff2` subsets — latin and latin-ext, normal and
italic where the family has both — with the SIL Open Font License text beside
each family and a README that states the family, the style, the weight axis, the
subset, the upstream address and the copyright holder for every file. A page
either declares its faces against this host or copies the files into its own
tree; the host only serves them.

Deployment is one task. `maak deploy` deletes
`/srv/http/jointhefreeworld.org/static-assets` recursively and copies the tree of
the current commit in its place. The GitHub Actions workflow on `trunk` hands
that task to the Byggsteg service and follows its log, with a concurrency group
so two runs cannot interleave, and a `workflow_dispatch` trigger for the case
where the serving machine was rebuilt and no commit is coming.

Four facts shape everything below. There is no manifest: nothing in the
repository enumerates what is served. There is no build: the images are committed
as they are served, and the README's advice on resizing is a `mogrify` command a
person runs by hand. There is no integrity check: a page can reference a path
that does not exist, and nothing notices until a reader sees a broken image.
And the deploy is destructive: between the delete and the end of the copy, the
directory is incomplete.

## The vision

1. **Every asset is addressable by content.** A digest in the name, or a digest
   beside a stable alias, so a page can cache a file forever and a replaced image
   needs no cache-busting query string. The deploy then becomes a synchronisation
   rather than a replacement.
2. **Committed sources, produced artefacts.** An image enters the repository once,
   at the size and format worth keeping, and a task produces the sizes, formats
   and crops the pages ask for. Two hundred megabytes of committed PNGs should be
   a build output with a byte budget, not the source of truth.
3. **The host is verifiable.** A manifest — path, bytes, digest, content type,
   licence, sha256 — generated by a task and asserted in CI, so that "what is
   served" is a file in the repository and a missing asset is a failing job
   rather than a broken page.
4. **A deploy cannot be half-done.** Publication writes a complete tree and then
   swaps it into place, so a failed or interrupted copy leaves the previous one
   serving, and the site is never a directory being filled.
5. **Provenance is uniform.** The fonts have a licence and a source beside every
   file; every image should have one too, in a form a mirror or a fork can carry.
   A shared origin that cannot be mirrored legally is not shared.

## Features that are in scope and not built yet

- **A manifest and a `maak verify`.** Nothing enumerates the tree today. The hard
  part is not the sha256: it is deciding the fields — licence, origin, the
  projects that reference a file — and keeping them true when a file is replaced.
- **An image pipeline.** The README already prescribes a resize by hand. The hard
  part is the policy: what the canonical width is, which formats are produced
  (WebP and AVIF as well as PNG), and how a page that asks for one is told the
  others exist without the host pretending to be a templating engine.
- **An atomic deploy.** The current task deletes and copies. The hard part is
  that the serving machine has no build: either the copy lands in a versioned
  directory and a symlink is swapped, or `rsync` deletes afterwards — and the two
  differ in what a reader sees mid-deploy.
- **A licence record beyond `fonts/`.** Three families have their OFL texts; the
  images do not say where they came from or who owns them. The hard part is
  authorship of the screenshots: some are of this collection's own programs, some
  are of somebody else's.
- **Deduplication.** The `-small.png` companions are hand-made derivatives, and
  several directories look like copies of one another. The hard part is that
  identical bytes under two names may both be referenced, so removing one needs
  the referencing side checked first — which is exactly what a manifest would
  make possible.
- **A size budget.** The repository grows with every screenshot and nothing
  measures it. The hard part is that a budget must fail a commit, and failing a
  commit over an image is a social problem before it is a technical one.

## New features that would be worth having

- **A `maak audit`** that reports total bytes, the ten largest files, the largest
  directories and every duplicate by digest, so growth is visible in a number
  rather than in a clone time.
- **A generated URL checker**: walk the sibling projects' sources for
  `static-assets/…` references and assert every path exists here. The cheapest
  possible end-to-end test of the whole host, and it runs without a server.
- **Server configuration in the repository**: a small `types` snippet, a cache
  policy that distinguishes a digest-named file from an alias, and a redirect
  map for renamed assets — because the deploy is a copy and the configuration is
  therefore the repository's business.
- **Root-level files for the host**: `robots.txt`, `security.txt` and a favicon
  set, which every other repository's site benefits from and no other repository
  owns.
- **A staging path** (`/static-assets-next/`) that a deploy fills first, so a
  change to an image can be looked at before it replaces the live one.
- **Per-project index pages** generated from the manifest — what this directory
  holds, at which sizes, under which licence — which is also the honest
  attribution page the collection currently lacks.
- **A `<picture>` helper for the frameworks** that consumes the derivative sets,
  in `olive-css` and `hygguile` rather than here, so the markup side stays where
  the markup lives.

## Contributions that would move the needle

1. **A non-destructive deploy.** One task, rewritten: copy into a new directory
   and swap a symlink, or `rsync` without `--delete` followed by a prune. The
   highest value per hour here, because the current version has a window in which
   the site is broken.
2. **A manifest with digests, plus `maak verify` and a CI step.** The foundation
   for everything else in this document: deduplication, cache policy, licence
   records and the URL checker all read it.
3. **An image task with a byte report** — re-encode, resize, and print before and
   after — because 217 MB of PNG is the heaviest payload the collection serves,
   and the change is measurable in one command.
4. **The URL checker** over the sibling repositories. Small, and it converts the
   most common failure in a shared asset host into a red build.
5. **A licence and attribution table** for the image directories, in the shape
   `fonts/` already uses. The work is asking, not writing.
6. **A size budget in CI**, once there is a number to budget against.
7. **A deduplication pass**, after the manifest makes it safe.

## Compared to related projects

| Project | What it is | Where static-assets differs |
| --- | --- | --- |
| A project's own `static/` or `public/` | The directory a web framework serves from, versioned with the code that uses it | Assets live with the code that references them and disappear with it; here they are shared, so one typography and one deploy serve many projects, at the price of no owner |
| jsDelivr, unpkg | CDNs that serve files out of git repositories and npm packages, with immutable caching | Content-addressed and cached at the edge, with no deploy at all; but they serve third-party code and libraries, not one collection's identity |
| An object store with a CDN (S3, R2) | Buckets and HTTP caching as a service, populated by an upload step | Durable, cheap and cacheable, with real immutability semantics; this host is a filesystem and a copy, which is why digests and cache policy have to be built by hand |
| Git-annex | A tool for managing large files with content-addressed keys and location tracking | Exactly the addressing this document argues for, and a far more capable answer than a manifest; the cost is a second tool in every clone |
| Guix, Nix | Content-addressed stores with substitutes, garbage collection and per-item provenance | The model to imitate at a much smaller scale: a digest names the thing, and the recipe that produced it travels with it |
| Wikimedia Commons | A curated, licence-audited commons of freely licensed media with per-file metadata | The provenance discipline worth copying; Commons is a public archive with review, this is a private host with one maintainer |
| Google Fonts | A hosted font service with subsetting and a stylesheet endpoint | What the `fonts/` directory deliberately replaces: self-hosted, no third-party request, licence text beside the file — at the cost of doing the subsetting by hand |
| IPFS, Arweave | Content-addressed, immutable web storage | Immutability by construction, which is the far end of the vision above and more machinery than a copied directory needs |

The others do four things this host should add: content addressing with immutable
caching (jsDelivr, IPFS), a store with recipes and garbage collection (Guix,
Nix), per-file licence metadata as a first-class record (Commons), and a
derivative pipeline that produces what pages ask for (every CDN and font service
above).

Where static-assets is ahead, and should stay ahead: one origin for the whole
collection, so a page's typography and its neighbour's cannot disagree; the
fonts self-hosted with the licence text beside the file, so no reader's browser
talks to a third party; a deploy that is a plain copy with no build service, no
bucket and no bill, which is why the whole thing fits in a repository and a
systemd timer; and a deploy pipeline that is a task in `maak.scm` rather than a
YAML file with steps in it, so a local run and the pipeline run the same code.

## In the long run

- **Content addressing as the default.** A digest per file, an alias for
  readability, and cache headers that follow from the name. Everything else here
  — deduplication, atomic deploys, a mirror — gets easier once that is true.
- **Sources in, artefacts out.** The repository holds what a maintainer chose and
  a recipe; the host serves what a page needs. That keeps the clone small and
  makes a new format an afternoon rather than a re-export of the tree.
- **A manifest other repositories read.** Once the collection's sites resolve
  assets through a manifest rather than a path guessed from a README, an asset
  can move without a broken page, and a page can fail its build instead of its
  reader.
- **Provenance for everything.** Licence, origin and author per file, in the
  shape the font directory already uses, so the host can be mirrored and forked
  without a scavenger hunt.
- **A serving configuration that lives beside the deploy**, because a host whose
  behaviour is only described by an nginx file on a machine is a host nobody can
  reproduce.

## Closing

The order that follows: make the deploy safe, then describe the tree in a
manifest, then derive and verify against it. The first is a task rewritten; the
second is the foundation the rest reads; the third is where the repository stops
being a copy of a directory and starts being a host.

*This document describes intent, not commitments.*
